### 0.2 產品與學習成功條件

產品定位為「車輛履歷與出售資訊展示平台」：讓展示帳號管理合成車輛、照片、自行申報維修與明確關聯的更正紀錄；讓訪客查詢已上架資訊。平台不提供購買、付款、過戶、站內聊天或聯絡賣家。

作業成功條件：開發者能不依賴 AI 說明 React → HTTP／Session／CSRF → Python API → PostgreSQL／檔案，以及 Docker、DNS、HTTPS 的完整運作與失敗處理。不以成交量、真實車籍驗證或高流量承諾為成功指標。

候選端到端驗收：

1. 訪客查看「僅供作業展示，資料為合成內容」提示，搜尋並閱讀已上架的車輛。
2. A 註冊後手動登入，建立合成 VIN 車輛，保存目前申報里程與主照片。
3. A 補登早於建立日、低於目前里程的合理歷史紀錄；以明確關聯更正錯誤紀錄，原文仍可追查。
4. A 設定售價並上架；訪客看到有效履歷、原文與更正鏈、來源標記，沒有購買或聯絡入口。
5. B 不能管理 A 的車、照片、更正或目前里程；A 下架提交後，新的受控讀取不再向非 Owner 提供該車內容。
6. A 登出或 Session 過期後，舊 Session 不能通過新的授權判定；同一 Cookie Session 的分頁清除私有狀態。
7. Docker 重建後資料與處理後的照片仍存在；最終可由自訂網域透過有效 HTTPS 操作。主機、費用與效能門檻仍待部署資源確認。

這是未來驗收腳本，尚未執行。下架／登出不保證追回已下載內容、已顯示畫面或撤回先前已授權的在途工作。

## 1. Problem Statement

### 1.1 目標使用者

- 二手車賣家：希望建立車輛資料、整理維修資訊，並在準備出售時公開展示。
- 二手車買家：希望先查詢車輛基本資料、價格、里程及維修紀錄，判斷是否值得進一步了解。
- 同一帳號可以同時扮演買家與賣家，不需要申請不同角色。

### 1.2 問題

二手車資訊可能散落在廣告、照片、對話與個人筆記中。買家不易一次看到一致的車輛資料與履歷，也容易把賣家自行填寫的內容誤認為經專業機構驗證的資料。賣家則需要一個容易維護、能控制何時公開的資訊頁。

### 1.3 提供的價值

Vibicle 將合成車輛資料、照片、展示售價與維修申報集中展示，讓使用者練習資訊整理、來源辨識與公開控制。允許補登合理歷史，並保留錯誤原文及明確的更正關聯。

本 MVP 僅供作業展示；「Owner」只代表平台內的資料管理者，不代表真實車籍所有人。首頁、Marketplace、詳情與註冊／新增車輛流程都需明顯提示「僅供作業展示，資料為合成內容，不供真實交易」。

UI 使用「查看車輛」「展示售價」「上架展示」「下架展示」「自行申報」「更正紀錄」；不得提供或暗示「立即購買」「付款」「聯絡賣家」「已認證車主」「履歷保證真實」。Marketplace 可以保留為頁名，但須搭配「出售資訊展示」說明。

共通條件：

- Frontend 可預先檢查，但 Backend 必須重新驗證身分、CSRF、Ownership、輸入與跨紀錄規則。
- 失敗不顯示成功；未登入、過期、越權、不存在、衝突、格式錯誤與服務失敗有可理解回饋，不揭露秘密或其他會員的私有資料。
- 提交中防止重複點擊；逾時依 NFR-REL-02 先查明結果，不盲目自動重送。
- UI 與獨立 API 均需驗收。不得將已停用的 AC 當成現行要求。
- 所有展示內容為合成資料；照片需為有權使用且無真實個資的展示素材。不承諾能自動辨識所有真實個資。

### FR-001 — 使用者註冊（Must Have）

- **描述**：以 Email + Password 建立展示帳號，遵守 OQ-01 的本輪候選基線。
- **操作流程**：開啟註冊頁 → 填寫資訊 → 送出 → 顯示結果 → 成功後前往登入。
- **前置條件**：尚未登入；輸入符合註冊規則。
- **正常結果**：建立一個無特殊角色的帳號，不自動登入，不取得任何他人的車輛。
- **錯誤情況**：格式錯誤、密碼不符、Email 重複、短時間大量請求、服務暫不可用。
- **Acceptance Criteria**：
  - FR-001-AC01：有效新資訊可完成註冊，之後可使用該憑證登入。
  - FR-001-AC02：不分大小寫或帶前後空白的同一 Email，不得建立第二個帳號；同時提交也不能重複建立。
  - FR-001-AC03：不合規輸入不建立帳號；失敗訊息不回傳既有帳號資料；密碼不出現在回應或日誌。
  - FR-001-AC04：註冊不宣稱 Email 已驗證、使用者是真實車主，或已取得機構資格。
  - FR-001-AC05：註冊成功僅引導手動登入，不能直接讀取車庫；註冊頁明示只供合成資料展示。

### FR-002 — 使用者登入與狀態恢復（Must Have）

- **描述**：Email + Password 驗證後建立 PostgreSQL Server-side Session，以 HttpOnly Cookie 傳遞不透明 Token；Store 存 Token Hash，CSRF 採獨立 Context Secret 的 Synchronizer Pattern。完整介面依 AUTH_DESIGN，CP-01／03／05／06；未實作。
- **操作流程**：開啟登入頁 → 填寫憑證 → 送出 → 成功後進入車庫；重新整理時檢查目前登入狀態。
- **前置條件**：帳號已建立，且憑證有效。
- **正常結果**：可以存取自己的受保護功能；畫面顯示登入狀態但不顯示秘密。
- **錯誤情況**：帳號不存在、密碼錯誤、達請求限制、登入過期、服務不可用。
- **Acceptance Criteria**：
  - FR-002-AC01：正確憑證登入後可查看車庫；有效期間內重新整理不需重複輸入密碼。
  - FR-002-AC02：不存在的帳號與錯誤密碼使用同一類失敗訊息；登入失敗不建立已驗證狀態。
  - FR-002-AC03：偽造、缺少或過期憑證不能讀取車庫或執行寫入；過期後提示重新登入，不把空車庫當作成功結果。
  - FR-002-AC04：Server 在距最後有效活動達 30 分鐘或距本次登入建立達 8 小時時拒絕 Session；Cookie 未到期也不能繞過；活動不能延長 8 小時絕對期限，舊 Session 不自動復活。
  - FR-002-AC05：有效活動限定為經定義且成功授權的業務 Request；照片、靜態資產、自動身分確認、背景輪詢與遭拒請求不延長閒置。以受控時間測試 29:59／30:00 與 7:59:59／8:00:00 邊界；具體活動清單在 API Contract 明列。
  - FR-002-AC06：每次成功登入使用新的 Session ID，替換並撤銷該 Browser 的舊本次 Session；舊 ID／晚到回應不能恢復它。不同裝置的獨立 Session 不因此失效。
  - FR-002-AC07：同 Origin 分頁在登入／登出通知、重新取得焦點或恢復頁面時重新確認目前身分；不得沿用先前帳號的私有快取或接受舊帳號請求結果。背景／凍結分頁恢復時先遮蔽私有內容再驗證，不承諾作業系統凍結時同步。
  - FR-002-AC08：登入與註冊也有 CSRF 防護；缺失／錯誤 Token 或不受信任 Origin 的 Browser 操作不得建立／替換有效登入。正常同 Origin 流程及符合 Contract 的獨立 HTTP Client 可成功。

### FR-003 — 使用者登出（Must Have）

- **描述**：終止本次登入，清除前端的會員私有狀態。
- **操作流程**：登入後點擊登出 → Server 確認終止 → 返回公開頁面。
- **前置條件**：已有登入；已過期或重複登出也應能回到未登入狀態。
- **正常結果**：撤銷目前 Server Session 並移除對應 Cookie；共用該 Cookie 的分頁一起失去身分，其他獨立 Session 不受影響。
- **錯誤情況**：網路中斷或 Server 無法確認登出；不得僅清除 UI 後就宣稱 Server 已撤銷憑證。
- **Acceptance Criteria**：
  - FR-003-AC01：撤銷提交完成後才進行 Session 授權判定的新 Request 必須拒絕原憑證，涵蓋讀取與寫入。已在撤銷前通過授權的在途工作不保證回溯取消；此界線不得描述成能撤回已完成操作。
  - FR-003-AC02：重新整理、上一頁與開啟分頁不恢復舊 Session；登出清除 App 私有 State／Query Cache／可控照片預覽。其他分頁依 FR-002-AC07 確認，已保存的外部副本不在可清除範圍。
  - FR-003-AC03：重複登出不造成錯誤資料；若無法確認 Server 端結果，顯示尚未完成或結果不明並允許重試。
  - FR-003-AC04：兩分頁共用同一 Session 時，A 登出後 B 的舊憑證遭拒；在正常可執行分頁的展示測試中，事件送達後最遲 5 秒清除私有 UI。另一 Browser／裝置的獨立 Session 仍可用；同 Browser 分頁不算獨立登入。
  - FR-003-AC05：登出／過期後晚到的查詢或續期回應，不得重新填入舊私有資料或重建失效 Session；登出不能以普通 GET 觸發，且需通過 CSRF 驗證。

### FR-004 — 查看自己的車庫（Must Have）

- **描述**：顯示目前會員擁有的全部車輛，含未上架與已上架。
- **操作流程**：登入 → 開啟車庫 → 查看列表與狀態 → 進入個別車輛管理。
- **前置條件**：有效登入。
- **正常結果**：只顯示自己的車輛；每台至少有品牌、車型、年份、里程、主照片或占位圖、上架狀態。
- **錯誤情況**：未登入、過期、查詢失敗；沒有車輛不是錯誤。
- **Acceptance Criteria**：
  - FR-004-AC01：A、B 各自建立車輛後，A 的車庫不包含 B 的車；修改查詢參數也不能取得 B 的私有車庫。
  - FR-004-AC02：新會員顯示空狀態與新增車輛入口；查詢失敗顯示重試，不誤顯示成沒有車輛。
  - FR-004-AC03：成功新增、編輯、上下架後，重新取得資料可看到已保存結果；Owner 可以查看自己未上架車輛的完整資料。

### FR-005 — 新增車輛（Must Have）

- **描述**：會員為自己的車庫新增車輛，預設未上架。
- **操作流程**：車庫 → 新增 → 填寫必填資料 → 送出 → 開啟車輛管理；照片可由 FR-012 補上。
- **前置條件**：有效登入；使用合成 VIN，正規化後尚未存在。
- **正常結果**：建立一台歸屬目前帳號的未上架車輛；即使尚無照片、售價或維修紀錄也能保存。
- **錯誤情況**：必填缺漏、VIN 格式錯誤／重複、年份／里程不合規、登入失效、保存失敗。
- **Acceptance Criteria**：
  - FR-005-AC01：有效資料只建立一台車，Owner 由登入身分決定；Request 不能指定其他 Owner。
  - FR-005-AC02：新車不出現在公開 Marketplace，訪客不能由直接網址讀取其詳情或照片。
  - FR-005-AC03：同一正規化 VIN 的先後或併發提交最多成功建立一台；失敗者得到可處理的衝突回饋。
  - FR-005-AC04：輸入與保存失敗時不留下可見的半成品車輛，也不對外揭露重複 VIN 所屬帳號。
  - FR-005-AC05：新增流程提示使用合成 VIN／合成車輛；公開只顯示末 6 碼，不宣稱 VIN 或 Owner 經車籍驗證。

### FR-006 — 編輯自己的車輛（Must Have）

- **描述**：Owner 編輯允許欄位；VIN 與 Owner 不能一般修改。目前申報里程可正常增加，誤填時可有理由地下修，但不能低於有效歷史最大值。
- **操作流程**：車庫 → 編輯品牌、型號、年份、目前申報里程、描述或售價 → 若下修里程則填理由並確認 → 保存；若有效歷史仍有錯誤高值，先依 FR-013 更正。
- **前置條件**：有效登入且是該車 Owner；資料仍符合當前狀態的規則。
- **正常結果**：保存後新的查詢反映有效修改；上架車同步公開。里程異動保留可追查前後值，沒有審核／自動認證。
- **錯誤情況**：非 Owner、車不存在、不合法欄位、目前值低於有效歷史最大值、下修缺理由／確認、移除已上架必要資料、併發衝突或保存失敗。
- **Acceptance Criteria**：
  - FR-006-AC01：Owner 可保存允許欄位，重新整理後內容一致；不能改 Owner、紀錄來源或申報時間。
  - FR-006-AC02：B 直接送出 Request 編輯 A 的車必須被拒絕，且所有欄位保持不變。
  - FR-006-AC03：【停用 v0.2】舊「目前里程不得下降」及混合價格規則由 FR-006-AC05～AC07 取代；原文與理由見 DECISIONS.md。
  - FR-006-AC04：不同分頁同時保存時不得默默覆蓋較新的版本；至少一方得到重新載入最新資料的衝突提示，保護方式待 Step 2。
  - FR-006-AC05：已上架車不得保存無效售價；一般文字／價格編輯不得直接改寫任何原履歷、更正版本、來源或申報時間。
  - FR-006-AC06：目前申報里程 C 必須在允許範圍且至少等於全部有效版本的最大里程 H；沒有有效紀錄時 H=0。已被更正取代的舊高值不得參與 H；與補登／更正同時發生時仍需保持 C≥H。
  - FR-006-AC07：降低 C 必須填理由、明確確認，並與前後值、Owner、Server 時間一起保存；有效歷史不符則拒絕且提示先更正。合法下修不會被已停用 AC03 阻擋；展示里程下修標記及摘要，不能悄悄抹除前值。

### FR-007 — 車輛上架（Must Have）

- **描述**：Owner 將完整的車輛資訊公開到 Marketplace。
- **操作流程**：車庫 → 選擇未上架車 → 補齊資料、有效售價與主照片 → 確認上架。
- **前置條件**：有效登入且為 Owner；必填資料、售價與有效照片齊備。
- **正常結果**：狀態變為已上架；訪客可以搜尋並查看允許公開的詳情、履歷與主照片。
- **錯誤情況**：非 Owner、缺價格／照片、資料失效、車不存在、併發變更或服務失敗。
- **Acceptance Criteria**：
  - FR-007-AC01：有效上架後，新的公開查詢包含該車；無維修紀錄的車仍可上架，顯示尚無紀錄。
  - FR-007-AC02：缺少必要資料時維持未上架；另一會員不能替車主上架。
  - FR-007-AC03：重複對已上架車執行上架不產生第二份刊登；成功必須以已保存結果為準。

### FR-008 — 車輛下架（Must Have）

- **描述**：Owner 停止公開展示，保留車庫、照片與履歷。
- **操作流程**：車庫／管理頁 → 點擊下架 → 確認 → 顯示未上架。
- **前置條件**：有效登入且為 Owner。
- **正常結果**：提交下架後，後續受控授權判定拒絕非 Owner 的詳情、履歷與照片讀取；不承諾追回已交付內容，精確邊界見第 5.2 節。
- **錯誤情況**：非 Owner、車不存在、併發修改、服務不可用。
- **Acceptance Criteria**：
  - FR-008-AC01：下架狀態提交完成後才進行的受控讀取／授權判定，不得向非 Owner 提供該車詳情、履歷或照片，公開列表的新查詢須排除該車；直接 URL、衍生圖與如有支援的條件／Range 請求同樣適用。
  - FR-008-AC02：Owner 仍可在車庫讀取完整資料；下架不刪除資料，建議保留售價供再次上架。
  - FR-008-AC03：重複下架不破壞資料；下架不代表已售出或已過戶。
  - FR-008-AC04：不保證撤回已下載檔、截圖、先前已顯示畫面、不遵循指示的外部 Cache 或下架前已通過授權的在途傳輸；已開啟的公開頁面下次重新取資料或恢復焦點時檢查狀態，得知下架後移除內容。
  - FR-008-AC05：從第一次交付即對車輛資料／照片設 no-store，App／受控 Proxy／CDN／Service Worker 不保留可繞過驗證的副本；下架後測試舊直接 URL、帶舊 ETag 的條件請求及新 Browser，均不能取得內容或有效 304。不能用無需重新授權的公開物件 URL 或未到期 Signed URL 滿足本條。

### FR-009 — 公開 Marketplace 與搜尋（Must Have）

- **描述**：訪客與會員可瀏覽及搜尋已上架車輛。
- **操作流程**：開啟 Marketplace → 輸入關鍵字 → 送出搜尋 → 查看結果 → 換頁或開啟詳情。
- **前置條件**：無須登入。
- **正常結果**：只顯示已上架車輛；依品牌或型號作不分英文字母大小寫的包含搜尋，固定最新上架優先，每頁 12 筆。
- **錯誤情況**：關鍵字超長、頁碼無效、查詢失敗；無匹配結果為正常空狀態。
- **Acceptance Criteria**：
  - FR-009-AC01：未登入者可操作；每張車卡顯示品牌、車型、年份、里程、TWD 售價、主照片與詳情入口。
  - FR-009-AC02：關鍵字 trim 後空白等同全部已上架車，最多 50 字元；整段輸入在品牌或型號任一欄位包含即可符合，不分英文大小寫，不暗中加入 VIN 或描述搜尋。
  - FR-009-AC03：每頁 12 筆，依最近一次由未上架轉為已上架的時間新到舊，同值再用穩定唯一識別排序；重複對已上架車上架、編輯或更正不刷新上架時間。換頁維持條件，改條件回第一頁，超出最後頁顯示空結果；併發上下架時不承諾跨頁快照完全不變。
  - FR-009-AC04：搜尋、換頁或手動更改條件皆不能讀取未上架車；查詢失敗顯示錯誤與重試；無結果顯示清除條件入口。

### FR-010 — 車輛詳情與維修履歷（Must Have）

- **描述**：訪客讀取已上架車的公開詳情；Owner 另可查看自己的未上架車。
- **操作流程**：Marketplace 點車卡／開啟網址 → 載入詳情 → 查看照片、基本資料、售價與履歷。
- **前置條件**：車輛存在，且為已上架或請求者為 Owner。
- **正常結果**：公開 VIN 僅末 6 碼，Owner 可看完整；主要履歷呈現有效版本，能展開原文、更正鏈與理由，固定標記自行申報。
- **錯誤情況**：車不存在、已下架、無權限、資料載入失敗、照片暫不可用。
- **Acceptance Criteria**：
  - FR-010-AC01：已上架車可在未登入下閱讀；沒有履歷顯示「尚無自行申報維修紀錄」，不得暗示零事故或從未維修。
  - FR-010-AC02：每筆有效紀錄顯示維修日期、里程、描述、申報時間及「車主自行申報・未經機構驗證」；依有效維修日新到舊，同日依里程大到小，再以申報時間／穩定識別排序。此順序只是顯示，不能把同日申報時間當成維修先後證據。
  - FR-010-AC03：公開資料不含帳號 Email、Password、登入憑證或未遮罩 VIN；非 Owner 不能以直接網址或額外請求取得私有欄位。
  - FR-010-AC04：深層連結重新整理可正常開啟；載入失敗不顯示成空履歷；照片失敗可顯示占位圖，不破壞其他資訊。
  - FR-010-AC05：每個維修事件僅目前有效末端計入履歷筆數／里程規則；被取代版本標示「已被更正，非目前有效值」，可依鏈查看原文、各版完整內容、理由及 Server 時間，不把更正當成多次實際維修。非 Owner 只能在車輛上架時讀取這些內容。
  - FR-010-AC06：首頁／註冊／Marketplace／詳情及車輛管理顯示合成資料與不供真實交易提示；無購買、付款、聯絡賣家、認證車主或真實車況保證文案／入口。
  - FR-010-AC07：若目前申報里程曾下修，詳情顯示可展開的更正摘要（前後值、理由與申報時間），不含帳號 Email；讀取依同一車輛公開規則。紀錄里程更正與目前值更正分開標示。

### FR-011 — 新增車主自行申報維修紀錄（Must Have）

- **描述**：Owner 為自己的車新增不可直接改寫的申報紀錄；沒有機構認證角色。
- **操作流程**：車庫／管理頁 → 新增維修紀錄 → 填寫日期、里程、描述 → 閱讀來源提示 → 送出 → 顯示新紀錄。
- **前置條件**：有效登入且為 Owner；車輛可為未上架或已上架；資料符合里程與日期政策。
- **正常結果**：保存紀錄與系統欄位，不自動改目前申報里程 C；可補登早於建立日／低於 C 的紀錄。依 BR-07／08／15 與有效版本驗證，已上架車的新履歷會公開。
- **錯誤情況**：非 Owner、車不存在、空描述、未來日期、里程不合規、與其他更新衝突、保存失敗。
- **Acceptance Criteria**：
  - FR-011-AC01：只有 Owner 可以新增；篡改請求中的 Owner、來源、申報者或系統時間不能改變系統認定結果。
  - FR-011-AC02：【停用 v0.2】舊「新紀錄里程≥目前里程、日期不可早於最近紀錄」阻止補登，由 FR-011-AC06 與 BR-07／08／15 取代。
  - FR-011-AC03：【停用 v0.2】取消新增履歷自動更新目前里程；以 FR-011-AC07 驗收新的一致性邊界。
  - FR-011-AC04：每筆固定標示自行申報與未驗證；不能選擇「已認證機構」來源。文字中填寫機構名稱也不改變來源標記。
  - FR-011-AC05：【停用 v0.2】自由文字補充不再作為數值更正機制，由 FR-011-AC08 與 FR-013 取代；原文見變更紀錄。
  - FR-011-AC06：允許任意順序補登 1900-01-01 至今日的事件，包括早於車輛建立日／低於 C；驗證 m≤C、嚴格較早日期最大有效里程≤m≤嚴格較晚日期最小有效里程。缺少一側則無該側限制；同日不推定先後，但整日區間需與前後日期相容。
  - FR-011-AC07：保存新事件時不修改 C；若 m>C，明確提示先更新目前申報里程而非偷偷提高或裁切 m。保存與當前有效歷史／C 的檢查必須一致；與補登、更正或目前里程更新併發時不能提交矛盾結果。
  - FR-011-AC08：原始版本不能直接編輯／刪除；更正需走 FR-013 的明確關聯，不能靠描述寫「前筆有誤」來排除原值。普通補登仍代表新事件，不會自動取代任何紀錄。

### FR-012 — 車輛主照片上傳與替換（Must Have）

- **描述**：Owner 為自己的車上傳或替換 1 張主照片；MVP 不做相簿、維修附件或影像編輯。
- **操作流程**：車輛管理 → 選擇照片 → 送出 → 驗證 → 保存 → 顯示新照片。
- **前置條件**：有效登入且為 Owner；車輛已建立。
- **正常結果**：照片與正確車輛關聯；上架前須有 1 張可用照片。替換成功後新的讀取顯示新照片。
- **錯誤情況**：非 Owner、車不存在、過大、格式不支援、內容不是有效影像、儲存失敗或上傳中斷。
- **Acceptance Criteria**：
  - FR-012-AC01：合法且不超過 5 MiB 的 JPEG／PNG／WebP 可保存；大小／內容需由 Server 驗證，不能只看副檔名或 Browser 宣告的類型。
  - FR-012-AC02：其他會員不能上傳或替換；超限、偽裝格式、損毀檔案均被拒絕且不改變車輛主照片。
  - FR-012-AC03：替換失敗時舊照片仍可用；成功替換不產生兩張「目前主照片」，也不混入其他車輛照片。
  - FR-012-AC04：未上架車照片僅 Owner 可透過服務讀取；下架後新請求依 FR-008 控制；服務／Container 重建後照片仍存在。
  - FR-012-AC05：Server 拒絕長／寬不在 1–6,000 pixels 或總像素超過 12,000,000 的影像；拒絕動畫／多頁、截斷、損毀或解碼資源超限，不只看壓縮後 5 MiB。第 5.2 節的工作預算需在選定部署資源上驗證。
  - FR-012-AC06：先依方向資訊正確轉正，再重編碼為允許的靜態格式，移除 EXIF／GPS／XMP／IPTC 與非必要文字 Metadata；輸出檔亦不超過 5 MiB。以含 GPS／拍攝資訊樣本檢查處理後檔案；原檔不可對外讀取，不承諾自動移除畫面中的車牌／人臉。
  - FR-012-AC07：照片及所有如有提供的衍生圖透過可檢查當前車輛狀態的路徑交付，從首次回應設 no-store；不能以儲存桶／原始檔／未到期公開連結繞過。替換後舊主照片 URL 不再由受控服務提供；失敗時仍保留原主照片。

### FR-013 — 明確關聯的履歷更正（新增 Must Have）

- **描述**：採 A 的精簡子集：單事件、單鏈、完整替代版本；不是自由文字補充，也不是通用審批／批次更正系統。原文不覆寫。
- **操作流程**：Owner 開啟有效紀錄 → 點「更正」→ 填替代日期、里程、描述及理由 → 檢查變更 → 提交 → 顯示新有效版本及原文連結。
- **前置條件**：有效登入、同一車輛 Owner、目標是該事件目前有效末端；候選歷史仍符合 BR-07／08／15。
- **正常結果**：新增不可直接改寫的更正版本並連到前一有效版；舊版本保留且退出有效值計算。C 不自動變動；如 C 也錯誤，Owner 另依 FR-006 下修並留理由。
- **錯誤情況**：跨車／非 Owner、目標不存在／不是目前末端、缺理由、替代日期／里程矛盾、超過 C、併發更正或保存失敗。
- **Acceptance Criteria**：
  - FR-013-AC01：只有 Owner 可更正同一車輛的目前有效紀錄；理由必填；系統決定申報者、Server 時間、來源及指向關係，不能指向另一車或任意偽造根事件。
  - FR-013-AC02：提交新增完整替代內容，保留所有舊版日期／里程／描述／來源／申報時間，不直接 UPDATE 原文或 DELETE 歷史；每個事件僅一個有效末端。
  - FR-013-AC03：以「排除被更正事件舊有效版，加入替代版」後的整體有效集合驗證日期／里程與 C；舊錯誤高值退出 H 及前後界線，不永久阻擋合理補登；不能忽略其他仍有效的高值。
  - FR-013-AC04：兩分頁同時更正同一末端，最多一方成功；另一方收到衝突並重新載入。不能產生分叉、循環、自我指向或一個版本被多次直接取代。
  - FR-013-AC05：更正不自動上／下調 C；先更正有效高值，再依法降低 C 的流程可完成。高於 C 的合法更正須先明確更新 C，不用隱含連動掩蓋目前值變更。
  - FR-013-AC06：Owner 及符合公開權限的訪客能展開原文、關聯、更正理由與各版本來源，主時間線只計一次有效維修事件；鏈也受下架權限限制。
  - FR-013-AC07：若更正仍有誤，可針對目前末端再追加更正；不可回頭直接取代非末端舊版。MVP 不含批次更正、分叉合併、審批、刪除、撤回事件或跨車重掛。
  - FR-013-AC08：失敗時新版本與有效末端切換均不生效；逾時先查明結果，不能把重試變成第二次維修。對鏈的限制仍須在重送及併發時成立。

### 5.1 日期、歷史里程、目前里程與更正

**定義**：

- 一個維修事件包含原始版本與其更正鏈；初始原文有效，新增更正版後只有末端有效。
- 有效集合 E 每個事件恰有一筆；H 是 E 的最大里程，E 為空時 H=0。被取代原文仍展示，但不得用於 H、前後界線或有效事件計數。
- C 為目前展示的自行申報里程上界，不自動從歷史推導，不宣稱為經認證的儀表觀測值。更新時間是 Server 申報時間，不是外部車況量測證明。
- 事件日期為 Asia/Taipei 日曆日期，1900-01-01 至今日。當日允許多次維修、相同或不同里程；沒有精確時間時不能按申報先後宣稱倒退。

**候選一致性規則**：

1. C 與每個 m 均在整數範圍，所有有效 m≤C。
2. 對任兩筆不同日期的有效事件，較早日期里程≤較晚日期里程；同日彼此不比較先後。
3. 補登 (d,m) 的下界是嚴格早於 d 的最大有效里程，上界是嚴格晚於 d 的最小有效里程；無前／後事件時省略相應界線。m 同時不得大於 C。
4. 更正先從 E 排除該事件舊有效版，再加入完整替代版，重新檢查規則 1–3。一次只更正一個末端；不提供忽略矛盾或批次原子修正多事件的例外。
5. 新增／更正歷史不修改 C；若事件真實申報里程超過 C，Owner 先更新 C，再提交。若輸入有誤，應更正該事件而非抬高 C 來掩蓋。
6. C 下修須先使所有有效歷史≤新 C，並留理由及前後值；若仍有另一有效高值，需先更正它，不能把整條歷史停用。下修不是取得真實里程認證。
7. 原文、更正版及有效末端切換需一起成功／失敗；與其他歷史／C 更新併發時須以一致狀態驗證。鎖定、版本、交易實現留待 System Design。
8. 不處理儀表歸零／更換、mile↔km 匯入或負里程；若要模擬這些情境須新增產品規則，不以「補充說明」繞過規則。

**產品驗收範例（合成資料，不是程式測試）**：

| 案例 | 候選預期 |
| --- | --- |
| C=80,000；2025-01-10=50,000，2025-03-10=70,000；補登 2025-02-10=60,000 | 接受；低於 C、早於車輛建立日也可；C 不變。 |
| 相同歷史補登 2025-02-10=45,000 或 75,000 | 拒絕，分別低於前日界線／高於後日界線；提示相關有效紀錄，限 Owner 可見。 |
| 2025-03-10 同日再新增 65,000 | 接受，該日區間為 65,000–70,000；若新增 2025-04-10=69,000 則拒絕，因低於較早日的 70,000。 |
| C=80,000；補登 2025-04-10=82,000 | 不自動更新 C；先明確更新 C≥82,000 再提交；或修正本次錯誤輸入。 |
| C=120,000；1 月有效 60,000、2 月誤填 110,000，欲補登 3 月 80,000 | 先新增指向 2 月有效版的更正為 70,000；舊 110,000 標示被更正、不參與規則，之後 3 月 80,000 可加入；C 仍 120,000。 |

### 5.2 照片處理、直接 URL 與 Cache 的保證範圍

**候選處理規格**：原始檔≤5 MiB、JPEG／PNG／WebP、單張靜態影像；寬／高各 1–6,000 pixels 且總像素≤12,000,000。拒絕動畫、多頁、不可解碼、截斷與超限內容，不能只信任副檔名、Content-Type 或壓縮大小。先處理方向，再重編碼，移除 EXIF／GPS／XMP／IPTC／非必要文字 Metadata；最終檔亦≤5 MiB，只交付處理後版本。

候選解碼工作預算為單張處理最多 5 秒、每個處理工作最多 128 MiB；超限要終止／拒絕、不破壞舊圖。這些值是本次審閱建議而非既有量測或已選定 Library 的保證。System Design 必須決定可實際執行的資源隔離及併行上限，並在部署資源驗證；若正常範圍圖仍超限，回到 DPQ-03 校準，不直接移除保護。像素限制與 Metadata 清理屬候選 Must Have，不再留到 Should Have。

原檔只作受限處理輸入，不對外提供，處理完成後清理暫存；失敗／孤立檔清理與授權發生順序待設計。重新編碼不等於能保證檔案無任何攻擊風險；不自動遮蔽畫面中的人臉／車牌。圖片需為有權使用且無真實個資的展示素材。

**下架能保證的事**：

- 狀態提交後才作出的新授權判定，以最新狀態控制完整詳情、全部履歷版本、主照片與所有衍生路徑；Owner 仍可讀。
- 從首次回應即對車輛動態內容與照片使用 `Cache-Control: no-store`；受控 Proxy／CDN 不快取，App 不持久化這些回應或用 Service Worker 提供離線副本。靜態程式／樣式資產不受此限制。
- 不把儲存桶／原檔網址公開；不接受「URL 很難猜」作授權；無需再驗證即可用至到期的 Signed URL 不符合本輪撤回界線。讀取可以不登入，但仍須驗證車輛目前已上架。
- 條件請求或如有支援的 Range／HEAD 也不得旁路，非 Owner 下架後不能拿到內容或用 304 延用舊資料；替換後舊主照片 URL 不再提供。
- 已開頁面在恢復焦點／下一次取資料時重新檢查，確認不可讀後清除 App 內容；不是即時推播追回畫面。

**不能保證的事**：已下載／截圖／外部備份、之前已儲存的 Browser 或不受控 Cache、已經交付到畫面的像素，以及下架前已授權的在途傳輸，不能靠下架或 HTTP Header 回溯抹除。若舊版曾公開長期 URL，需在發布前停用舊入口／清理受控 Cache，但仍無法保證外部副本消失。無離線隱私撤回或網際網路全域刪除承諾。

參考：[MDN Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control) 說明 Cache 指示不會清除所有既有副本；[OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) 說明內容驗證、影像處理與資源限制。數值界線是本專案候選政策，不是來源給出的通用門檻。

### 5.3 Session、登出、CSRF 與跨分頁

以下是 Step 2C.5 已接受的設計約束（CP-01～06）；產品 AC 原文不變，詳細流程參照 [AUTH_DESIGN §4～6](AUTH_DESIGN.md) 及 [Database Design §4.2／8](DATABASE_DESIGN.md)。

- **Credential／Store**：Email 驗證器 normalized→PG lower、單一canonical Unique；Password仍12–128字元、可貼上／不強制組合／不trim或截斷、註冊後手動登入；Hash選Argon2id。PG Encoding／Collation／Locale／Library版本與Unicode測試須記錄，不宣稱所有大小寫／視覺相似問題已解決（CP-04）。
- **Context**：Cookie攜帶32-byte安全隨機Token的base64url，PG只存SHA-256摘要；每個preauth／authenticated列另有獨立32-byte csrf_secret、無共用Default／不需Index（CP-01）。preauth user_id=NULL、建立起絕對15分鐘且不Touch；authenticated有User、閒置30分鐘／絕對8小時，等號拒絕（CP-03）。
- **Rotation**：每次成功登入新Token＋新Secret、新列；同短交易撤銷Browser帶來的舊Context，禁止就地升級preauth／沿用ID。只影響本次Context，不撤銷其他裝置（CP-03／05）。
- **Cookie**：Production __Host-vibicle_session，Secure、HttpOnly、SameSite=Lax、Path=/、無Domain；authenticated Max-Age=28800、preauth=900。只有受控Bootstrap／成功Login／確認Logout設定或清除Cookie；普通API／me／Touch／錯誤Response不重送Set-Cookie。實際Origin、TLS、可信Proxy仍須配置／測試（CP-05／06）。
- **CSRF**：採Synchronizer Token；JS透過受控HTTPS／no-store介面取Token，記憶體保存、Mutation用X-CSRF-Token回傳，常數時間比對Cookie對應Context；SID仍HttpOnly。涵蓋Register／Login／Logout／車輛／C／上下架／補登／更正／照片，不得用Token單獨取代登入（CP-01）。
- **來源**：固定PUBLIC_ORIGIN精確比scheme／host／有效port。Origin存在必合法且匹配（null／多值／錯誤拒絕），缺失才檢查Referer；兩者全缺拒絕。Mutation及CSRF Bootstrap若有Sec-Fetch-Site只接受same-origin；獨立HTTP Client需Cookie Jar＋Token＋明確合法Origin，不略過保護。同Origin不免CSRF、SameSite／CORS不替代Token（CP-01／06）。
- **技術Bootstrap／Gate**：Get CSRF Context只建立／重用安全上下文，不登入／登出／改業務資料；有效Context重取不換Token／Cookie、不續期。Fixed Window Gate可在CSRF拒絕前計數，拒絕不得有業務／登入副作用，不宣稱技術計數完全不變（CP-01／02）。
- **Touch白名單**：成功且完整授權的管理Mutation（含合法管理No-op）、Owner主動車庫／管理詳情／完整履歷讀取可Touch；公開頁／搜尋、me、csrf、圖片／靜態、背景輪詢／預抓、拒絕／未成功請求皆不可。No-op不改刊登時間或未變動的車輛版本。MVP不自動輪詢Owner讀取，不以human=true證明人類活動（CP-05）。
- **Touch原子語意**：業務交易結束後另用短Session交易；鎖後取新Clock，重驗kind、revoked與兩期限，僅條件UPDATE last_activity。不能改created／absolute／Secret、清revoked或UPSERT。業務已Commit但Touch失敗／過期，必須保留已保存事實，不能誘導盲重送（CP-05）。
- **Logout例外**：已保留的失效authenticated列可在正確原CSRF＋來源下專用確認撤銷／清Cookie；有效preauth也可安全登出；未知／已清理列或過期preauth需新安全Context。此例外不授予一般受保護API身分、不Touch。只有確認撤銷後宣告成功；網路不明不得假稱Server未執行（CP-05）。
- **分頁／在途界線**：同Cookie Jar共用登入；撤銷Commit後開始的新受控判定拒舊ID，先授權工作不回溯取消。Auth Epoch＋User綁定、BroadcastChannel清私有State／Cache／可控預覽；通知送達可執行Tab後≤5秒清理，焦點／BFCache恢復先遮蔽重驗（CP-06）。
- **Design Risk仍開放**：Browser可能先處理舊Response的Set-Cookie再讓JS忽略JSON；Web Locks僅是受控Auth Lifecycle候選，不保證所有外部／非受控請求順序；單次me匿名不能證明前一Login已結束。Timeout／凍結／Cookie重排必須實測，不降低FR-002-AC06／07或FR-003-AC05；見DECISIONS §6的DR-01（CP-06）。
- **驗收／恢復**：測正常同Origin、Native Client、缺失／跨Context Token、來源缺失、Logout／上傳；正常重啟保留有效Session原期限，Backup Restore在隔離下失效全部Session含preauth再開流量。Cookie存在與清理延遲不影響Server到期拒絕。

依據：[OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet)、[OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)。這些是設計依據，未執行安全測試。

### 9.4 尚存風險與已明定的限制

- **資料真實性**：VIN 唯一、追加原文、關聯更正都不是車籍或車況認證；只用合成資料並固定來源／展示標記。
- **目前值更正的濫用**：允許有理由下修 C 才能復原錯值，但也可能被拿來自述較低里程；保留可見前後值與歷史，不宣稱能防止真實世界欺詐。
- **多筆錯誤互相限制**：單次更正仍須保持其他有效事件一致；若多筆誤填，要依相容順序逐筆修正，介面提示阻擋紀錄。MVP 不含批次修正或任意刪除；不可為解鎖而默默忽略有效事件。
- **關聯更正成本**：FR-013 增加版本、並行及展示成本。若刪除此 Must Have，就必須回頭降低數值更正／有效歷史要求，不能用純文字補充假裝等價。
- **下架不是追回副本**：已交付畫面、截圖、外部 Cache、已授權串流不可保證消失；從首次交付限制受控快取、封閉儲存旁路。
- **Session 邊界**：同 Cookie 分頁是同一次登入；已授權在途工作不回溯取消。Server 撤銷／過期是安全邊界，事件通知只改善 UI。
- **影像處理**：5MiB 不是解碼資源界線；尺寸／重編碼／去 Metadata 仍不能保證抵抗所有解析器攻擊，需 SDQ-03／DPQ-03 實際驗證。
- **展示公開與費用**：未定主機／網域／預算，也未授權對真實資料開放；效能無目前 SLA。範圍或資源變更需回寫 Decision Log。
